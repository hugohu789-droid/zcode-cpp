# Java 原版与 C++ 的性能对比

- 日期：2026-10-21
- 测量环境：同一台机器、同一时段，Windows 11

| | |
|---|---|
| Java | JDK 1.8.0_501 HotSpot，默认参数；每个工作负载在独立 JVM 中运行，先预热 10 次，再计时 15 次 |
| C++ | MSVC 17.14 Release；计时 9 次 |
| 工具 | `tools/golden-java/.../JavaBench.java`（`tools/bench_java.ps1`）与 `bench/zcode_bench.cpp`（`tools/bench.ps1`） |

两边跑的是同一套工作负载、同一份输入（取自 `testdata/`）。参与对比的有三个版本：

- **Java**：打过补丁的原版。它和当前 C++ 的行为一致，校验和也相同。
- **C++ 忠实移植**：commit `4fb3352`，Phase 2 的逐行移植，尚未优化，对照的是未修复版的 Java。
- **C++ 最终**：当前版本。

## 1. 稳态耗时（JIT 预热后，取最小值）

| 工作负载 | Java（三轮最小值的范围） | C++ 忠实移植 | C++ 最终 | Java ÷ C++ 最终 |
|---|---:|---:|---:|---:|
| splice_all_severe：30,952 组键序列，严格模式 | 44.3–45.9 ms | 75.0 ms | 22.5 ms | 2.0× |
| splice_all_fuzzy：同上，fuzzy 模式 | 91.2–92.5 ms | 187.0 ms | 45.1 ms | 2.0× |
| typing_severe：659 个词的每个前缀，`shape()` | 6.5–7.6 ms | 9.3 ms | 3.5 ms | 1.8–2.1× |
| typing_fuzzy：同上，fuzzy 模式 | 22.9–23.2 ms | 53.8 ms | 13.0 ms | 1.8× |
| keys_stateless_severe：逐键，每次整串重新拼接 | 3.9–4.1 ms | — | 1.69 ms | 2.3× |
| keys_stateless_fuzzy | 21.3–21.4 ms | — | 10.9 ms | 2.0× |
| heavy_fuzzy：6 个候选特别多的输入 | 16.6–16.9 ms | 41.9 ms | 8.2 ms | 2.0× |

**逐键输入（IME 实际用法）**：Java 原版没有增量接口，每按一个键都要整串重新拼接；C++ 可以用 `Session`。

| 模式 | Java，每键整串重算 | C++ `Session` | Java ÷ C++ |
|---|---:|---:|---:|
| 严格模式 | 3.9–4.1 ms | 0.76 ms | 5.2× |
| fuzzy 模式 | 21.3–21.4 ms | 8.98 ms | 2.4× |

## 2. 冷启动

| 指标 | Java | C++ 最终 |
|---|---:|---:|
| 进程启动 | JVM 启动约 163 ms（`java -version`，5 次中位数） | 测试程序整个进程约 15 ms（含 GoogleTest 初始化） |
| 进程启动后到第一个结果 | 103–325 ms（4 次运行；类初始化、反射、首次解释执行） | 1.7 ms（解析内嵌数据表、建表、第一次 `shape`） |
| splice_all_severe，JVM 中首次运行（未预热） | 154–174 ms | 22.5 ms（没有 JIT，首次运行即为稳态） |
| splice_all_fuzzy，首次运行 | 127–207 ms | 45.1 ms |

## 3. 解读

1. **最终版 C++ 约为预热后 Java 的 2 倍**。在 IME 的逐键场景下，用 `Session` 是 2.4–5.2 倍。冷启动和刚启动后的前几次调用差距更大：首个结果 1.7 ms 对 100–300 ms，此外 JVM 本身启动还要约 160 ms。
2. **逐行忠实的 C++ 移植反而比预热后的 Java 慢**，约为 Java 的 0.4–0.6 倍。原版代码大量分配短命小对象：每次扩展都复制整个序列，每次调用都新建列表。JVM 用线程本地的指针递增分配（TLAB）加逃逸分析，处理这类对象非常便宜；逐行翻译成 C++ 后，每个对象都要走一次堆分配。C++ 的优势来自 Phase 3 对数据结构的改造（arena、预计算表、精确分配），而不是语言本身。
3. 按场景看：
   - 下游以独立进程加 IPC 的方式使用本库，进程只启动一次，所以稳态那 2 倍最有参考价值；
   - 冷启动差距关系到进程拉起后的首次响应速度；
   - `Session` 关系到每按一个键的延迟。

## 4. 口径说明（影响公平性的因素）

- **日志**：Java 用的是空日志实现。但原版在每次拒绝候选时都调用 `logger.info("…", clss.toString(), …)`，`toString()` 在判断日志级别之前就已求值，这部分开销计入了 Java 的耗时。原服务实际配置的是 INFO 级别并写入文件，那样会额外产生日志 I/O，这里**没有测**，实际运行只会比表中更慢。
- **范围**：两边都只测拼接引擎（分解 + 拼接 + 生成输出串），不含原服务的 BK 树词典匹配、线程池和 HTTP。
- **校验和**：
  - splice、keys、heavy 三类工作负载，两边的候选数和码位数完全一致；
  - typing 两项略有差异：严格模式 3,793 vs 3,798，fuzzy 60,414 vs 60,423。原因是 C++ 按 UTF-8 字节取前缀、Java 按 UTF-16 码元取前缀，少数含非 ASCII 字符的词在 C++ 里会多出几次调用。也就是说 C++ 在这两项上做的工作略多，这里给出的倍数对 C++ 是偏保守的。
- **波动**：Java 受 GC 影响，同一轮里的中位数有时明显高于最小值，例如 typing_severe 的最小值 6.5 ms、中位数 8.2–17.5 ms。表中取最小值，即各自的最好情况。
- **未测**：内存占用；更新版本 JDK（17/21）的表现；Linux 上的表现。
